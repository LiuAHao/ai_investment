# 多 Agent 逻辑修复方案（含自审 grill）

> 依据：`docs/多Agent链路与逻辑问题审查.md`（复核版）
> 范围：只修逻辑与可靠性问题，不改产品定位、不换数据源、不引入新框架
> 原则：先行为正确性，再成本，再体验；每一阶段可独立上线、可回滚

## 〇、决策总表（推荐答案）

| 决策 | 推荐 | 放弃的方案 | 理由 |
| --- | --- | --- | --- |
| 第二轮调研 | 条件执行 + 单 Agent 回退第一轮 | 无条件保留 / 直接删除 | 保留跨 Agent 信息共享的设计意图，只在有共享发现时付成本 |
| function calling 降级 | 仅对"模型不支持工具"永久降级；网络类错误重试 1 次 | 任何异常永久降级 | 抖动不应永久剥夺工具能力 |
| 置信度 | 由可观测信号计算，缺数据时硬上限 0.55 | 沿用模型自评 + 0.85 默认 | 自评不可验证，空数据必须体现出来 |
| 多轮上下文 | 同一会话内复用 `session_id`，后端继承上一轮资产与结论摘要 | 新建追问 UI / 暂不实现 | 零 UI 成本即可恢复"追问"，风险可控 |
| 工具超时 | 数据层设网络超时 + 线程兜底 | 只加线程兜底 / 只加网络超时 | 网络超时治本，线程兜底覆盖 akshare 等无超时接口 |
| 会话落盘 | 独立写锁 + 唯一临时文件名 | 维持现状 / 全量重写改增量 | 现状已验证会并发报错，改动小 |
| 会话文件 | 加入 `.gitignore` | 保持可提交 | 含用户问题与研报，不应入库 |
| 派发计划 | 去重 + JSON 模式（可回退） | 维持正则解析 | 去重防重复工位，JSON 模式降低回退率 |
| 解析 unknown | 连续 2 次未知则强制收敛 | 继续循环 | 防止空转烧迭代 |
| 收敛指令 | 按 Agent 角色传入期望格式 | 统一 FINAL 文案 | 汇总 Agent 需要 JSON，调研 Agent 需要 FINAL |
| 展示一致性 | 删除 `round1Summary` 死状态 | 双结论并列展示 | 第二轮完成后现状已覆盖，双展示增加认知负担 |
| 死字段 | 删除 `scenarios/action_options/data_limitations` | 保留待用 | 全链路无写入无渲染，保留只会误导 |
| 沉淀门槛 | 收紧阈值 + 要求真实证据 + 单线程异步 | 只收紧 / 只异步 | 生成内容回灌知识库需要质量与串行双重约束 |
| 工具结果截断 | 结构化截断（长字段/长数组压缩） | 硬切 3000 字符 | 硬切已实测产生非法 JSON 文本 |
| 轮询窗口 | 退避轮询至约 15 分钟 | 固定 3 分钟 | 两轮任务可能超过 3 分钟 |
| SummaryAgent 工具 | 显式核实工具白名单 | 保持全放开 | 汇总阶段只需核实关键数字 |
| 会话保留 | 单会话回合上限 + 文件大小上限 | 不限制 | 全量重写成本随文件增长 |

## 一、阶段划分

- **P0（行为与成本，1 个 PR）**：第二轮条件执行与回退、降级策略、置信度、unknown 收敛、派发去重、SummaryAgent 白名单、轮询窗口。
- **P1（可靠性，1 个 PR）**：工具超时、会话落盘并发、`.gitignore`、沉淀门槛与异步、结构化截断、会话保留。
- **P2（一致性清理，1 个 PR）**：多轮上下文继承、死字段/死状态清理、证据引用语义。

每个阶段独立可上线；P0 不依赖 P1/P2。

## 二、P0：行为与成本

### P0-1 第二轮条件执行与回退

**改动**（`src/agents/orchestrator.py`）

1. 第二轮触发条件：`full_findings` 非空，且至少满足其一：
   - 发现条数 ≥ 2；
   - 发现来自 ≥ 2 个不同 Agent。
   不满足则跳过，日志与行为一致。
2. 第二轮单 Agent 迭代上限下调（如 `max_iterations=3`），通过 `supplement()` 传入，避免补调研变成第二次全量调研。
3. 结果合并：逐 Agent 比较第一轮与第二轮：
   - 第二轮 `error` 非空、`degraded=True` 或 `conclusion` 为空 → 用第一轮；
   - 否则用第二轮。
   `AgentResult` 增加 `round1_conclusion: Optional[str]` 仅用于日志/排查，不进入前端协议。
4. 事件序列保持现状（round=1/2），前端无需改动。

**自审 grill**

- Q：为什么不是"有发现就跑、没发现就跳过"这么简单？
  A：一条低价值发现也会触发全量第二轮，成本仍翻倍。加"≥2 条或跨 2 个 Agent"把"确有共享"与"模型随手广播"区分开。
- Q：为什么保留第二轮而不是直接删？
  A：第二轮是重构版的核心设计（跨 Agent 交叉验证）；直接删除会改变产品语义。条件化保留，风险最低。
- Q：回退用"第二轮为空/降级"够不够？第二轮内容更差但非空怎么办？
  A：无法自动判断"更好"，只能判断"可用"。接受该局限，并在结果中保留第一轮结论便于人工排查。
- Q：第二轮迭代 3 次会不会太紧？
  A：第二轮任务只是"核实/补充"，3 次足够；如实际偏紧，可由 env 单独配置，不与第一轮共享 `AGENT_MAX_ITERATIONS`。

### P0-2 降级策略

**改动**（`src/agents/loop.py`、`src/agents/events.py`）

1. 区分错误类型：
   - 模型/接口明确不支持 tools（参数错误、unsupported 类异常）→ 立即永久降级；
   - 网络、超时、限流 → 重试 1 次（0.5s 退避）后仍失败才降级。
2. 新增事件 `agent_degraded`（agent、原因、是否永久），前端 `AgentCard` 显示"已降级为文本工具协议"。
3. 文本协议路径补上 `_check_progress`，与 function calling 路径一致。

**自审 grill**

- Q：靠异常文本判断"不支持工具"可靠吗？
  A：不可靠，但比"一律永久降级"好。实现上用异常类型优先（`BadRequestError`/`TypeError`），文本匹配仅作兜底；误判代价是多重试一次。
- Q：重试会不会让本来就慢的任务更慢？
  A：只重试 1 次且仅网络类错误，最坏多一次往返；相比永久失去工具能力，可接受。
- Q：加事件会不会影响历史回放？
  A：新增事件不进入 `agent_results`，只影响实时视图；历史渲染走 `TurnDetail`，无需处理。

### P0-3 置信度

**改动**（`src/agents/summary_agent.py`）

输入从"模型自评 + 自己工具失败率"改为：

```
base = model_confidence if provided else 0.6
扣分：
- 调研 Agent 降级/失败比例 r：-0.3 * r
- 全部调研工具成功次数为 0：直接封顶 0.55
- information_gaps ≥3：-0.1；≥5：再 -0.1
- 多空任一侧为空：-0.05
- SummaryAgent 自身工具失败率 >50%：-0.1
degraded=True（自身异常）：min(base, 0.4)
```

产出仍写 `answer.confidence`，前端展示逻辑不变。

**自审 grill**

- Q：0.55/0.6/0.3 这些数字有依据吗？
  A：没有理论依据，是可解释的经验值。目标不是"准确概率"，而是让"没数据"必然低分、"数据齐"才可能高分；阈值集中在一处便于后续调整。
- Q：要不要把置信度拆成多个维度展示？
  A：暂不。前端已有"可信度"标签，多维展示属于产品改动，留到提出明确需求后。
- Q：调研 Agent 失败比例是否需要包含"工具失败但结论非空"？
  A：包含。工具失败但结论非空恰恰说明结论缺数据支撑，应扣分。

### P0-4 unknown 决策收敛

**改动**（`src/agents/loop.py`）

- function calling 与文本协议两条路径都维护 `unknown_streak`；
- 连续 2 次 `unknown` → `_force_converge()`；
- 每条 unknown 仍作为思考记录，但不再无限追加 assistant 消息（保留最近 2 条即可）。

**自审 grill**

- Q：会不会把"模型正在思考、还没准备输出"误判为卡住？
  A：2 次阈值已给模型一轮缓冲；且状态可从事件日志观察，必要时调成 3。
- Q：为什么限制 assistant 消息数量？
  A：unknown 内容多为无结构散文，累积会挤占上下文并降低后续收敛质量。

### P0-5 派发计划去重与结构化

**改动**（`src/agents/orchestrator.py`）

1. `agents` 列表去重且保持顺序；
2. 优先使用 `response_format={"type": "json_object"}`（模型不支持时捕获异常回退现有正则）；
3. 解析失败/为空回退关键词规则时，记录一条 `orchestrator_thinking`（当前静默回退，排查困难）。

**自审 grill**

- Q：DeepSeek 不一定支持 `json_object`，值得加吗？
  A：支持则显著降低解析失败率；不支持就走回退，无额外风险。异常捕获范围限定在参数/格式错误。
- Q：去重后还要不要在提示词里约束？
  A：要，提示词写"每个 Agent 最多一次"，代码去重作为兜底。

### P0-6 SummaryAgent 工具白名单

**改动**（`src/agents/summary_agent.py`）

`tool_names` 显式列出核实类工具：`cn_stock_history`、`cn_stock_spot_search`、`asset_news_search`、`investment_framework_search`（按现有注册名）。

**自审 grill**

- Q：限制后汇总阶段还能核实基金/ETF/美股吗？
  A：上述四类覆盖主流程；如出现明确的跨市场核实需求，再把对应工具加入白名单。白名单显式化本身就是可审计的收益。
- Q：会让"综合分析"更依赖调研结论吗？
  A：是，符合提示词里"其余情况直接基于调研结果分析"的既有约束。

### P0-7 轮询窗口

**改动**（`src/web/src/hooks/useAgentStream.js`）

- 轮询改为退避：1.2s → 2s → 3s 上限，总时长约 15 分钟；
- 超时文案明确提示"可到历史记录查看结果"（后端任务可能仍在跑）。

**自审 grill**

- Q：15 分钟会不会让用户干等？
  A：SSE 正常时不会走到轮询；只有断流才轮询。真正问题是"任务还在跑但前端提前判失败"，延长窗口比误报失败更合理。
- Q：为什么不直接依赖 SSE 重连？
  A：后端进程重启会丢 `_tasks` 与事件缓冲，SSE 只能保持空连接；轮询至少能覆盖"同一进程内断流"。

## 三、P1：可靠性

### P1-1 工具超时

**改动**

1. 数据层：`src/data/*`、`src/tools/*.py` 中的 HTTP 调用显式设置连接/读取超时（requests 用 `timeout=`，httpx 同理）；
2. 兜底层：`BaseTool.run()` 用守护线程 + `timeout` 执行，超时返回 `status="failed", error="工具执行超时"`；
3. `ToolSpec.timeout_seconds` 与 `BaseTool.timeout` 真正生效。

**自审 grill**

- Q：线程超时后底层调用仍在跑，会泄漏吗？
  A：会。守护线程不阻止进程退出，但持续挂起会占资源。因此先做网络层超时（治本），线程兜底只作为最后防线，并在超时后记录日志便于定位具体工具。
- Q：为什么不用 signal？
  A：只在主线程可用，Agent 跑在线程池里，不适用。
- Q：超时值怎么定？
  A：沿用各工具现有 `timeout`（10~30s），行情类 20s、知识库 10s；不新增配置项。

### P1-2 会话落盘并发

**改动**（`src/agents/memory.py`）

1. 新增独立 `_save_lock`，`_save()` 全程持锁；
2. 临时文件名加入进程与线程标识，避免共享 `.tmp`；
3. 落盘失败保留原文件，记录一次错误日志（不刷屏：同类错误 60s 内只记一次）。

**自审 grill**

- Q：为什么不把 `_save` 放进现有 `_lock`？
  A：现有锁保护内存结构，落盘是慢 IO，混用会阻塞读接口（`/api/history`）。独立写锁更清晰。
- Q：要不要改成增量写入或数据库？
  A：当前数据量与调用频率不需要；引入数据库是架构变更，超出修复范围。
- Q：多进程部署怎么办？
  A：当前是单进程 Flask；多进程需要文件锁或外部存储，列为已知边界，不在本次范围。

### P1-3 `.gitignore`

**改动**：加入 `src/data/sessions.json`（及其 `.tmp` 变体）。同时确认 `src/rag/index/chroma/`、`*.db` 已覆盖。

**自审 grill**

- Q：直接忽略整个 `src/data/*.json` 吗？
  A：不。该目录可能有需要入库的静态数据，只忽略运行期会话文件。

### P1-4 沉淀门槛与异步

**改动**（`src/rag/indexer.py`、`src/agents/orchestrator.py`、`src/rag/config/rag_config.json`）

1. 门槛：`min_summary_chars` 50 → 120，`min_key_points` 1 → 2，新增 `min_confidence=0.6`；
2. `has_evidence` 改为"存在至少 1 条真实工具成功记录"（`ToolResult.status == "success"` 且 `data` 非空），不再用 `evidence_refs` 是否非空；
3. 沉淀改为单工作线程队列消费，研究结果返回后异步执行；失败只记日志。

**自审 grill**

- Q：异步后进程退出会丢沉淀吗？
  A：会丢未消费任务。接受该代价：沉淀是辅助能力，不能影响主结果；消费线程用守护线程 + 启动日志。
- Q：并发写 Chroma 会不会锁冲突？
  A：单工作线程串行写入即可规避。
- Q：收紧门槛会不会几乎不沉淀了？
  A：会显著减少，这是目的。生成内容回灌知识库的风险高于沉淀数量不足。

### P1-5 工具结果结构化截断

**改动**（`src/agents/loop.py`）

- 不再按字符硬切。对序列化结果按结构压缩：
  - 长字符串保留前 500 字符；
  - 长数组保留前 20 条并标注"共 N 条"；
  - 总预算 6000 字符，超出再按字段逐层裁剪；
- 保证回填给模型的内容始终是合法 JSON。

**自审 grill**

- Q：结构化压缩实现复杂度值得吗？
  A：值得。硬切会让模型读到破碎 JSON，直接影响结论质量；压缩逻辑约 30 行，集中在一个函数。
- Q：为什么预算从 3000 提到 6000？
  A：结构化压缩后信息密度更高，适度放宽可减少关键字段丢失；上限仍受模型上下文约束。

### P1-6 会话保留

**改动**（`src/agents/memory.py`）

- 单会话最多保留 200 轮，超出淘汰最早回合；
- 会话总数与总文件大小设上限（如 20MB），超出淘汰最旧会话；
- `/api/history` 仍只返回列表，不受影响。

**自审 grill**

- Q：淘汰历史会丢用户数据吗？
  A：会。但当前没有导出能力，无限增长最终会导致每次落盘变慢直至不可用；上限设得足够宽（200 轮）即可。
- Q：为什么不用分页读取代替淘汰？
  A：分页解决读取，不解决落盘成本；两者可以并存，但落盘上限必须存在。

## 四、P2：一致性清理

### P2-1 多轮上下文最小实现

**改动**

1. 前端：`useAgentStream.start()` 在"新对话"前复用当前 `sessionId`；`reset()` 清空。`App` 的底部输入条在 `done` 状态下继续可提交；
2. 后端 `OrchestratorAgent.run_query`：当 `context` 为空且 `session_id` 命中历史时，取上一轮 `answer.summary`（截断 1500 字）+ 上一轮资产作为上下文；
3. `_resolve_assets` 的 `previous_assets` 分支真正实现：本轮未识别到资产时继承上一轮资产。

**自审 grill**

- Q：这会不会改变"每次都是新任务"的现有行为？
  A：会，但仅在用户不点"新对话"时生效，符合直觉；点击"新对话"仍然完全重置。
- Q：历史很长时把上一轮摘要塞进 prompt 会不会污染？
  A：只放最近一轮且截断 1500 字，风险可控；不做全历史拼接。
- Q：资产继承会不会导致用户换了标的仍沿用旧资产？
  A：仅在本轮解析为空时继承；本轮解析出资产则以本轮为准。

### P2-2 死字段与死状态清理

**改动**

- 删除 `InvestmentAnswer.scenarios`、`action_options`、`data_limitations`；
- 删除前端 `round1Summary`（`useAgentStream` 与事件处理中的相关分支）；
- `AgentCard` 继续只展示当前 `summary`。

**自审 grill**

- Q：删字段会影响历史文件兼容吗？
  A：Pydantic 默认忽略额外字段，旧 `sessions.json` 中的多余键不会导致加载失败；已用 `model_dump` 的结构验证过解析路径。
- Q：将来要展示"情景分析"怎么办？
  A：需要时再加，届时提示词、解析、渲染一起改；保留空字段只会制造"看起来有功能"的假象。

### P2-3 证据引用语义

**改动**（`src/agents/loop.py`）

- `evidence_refs` 改为 `tool_name:step_id`（无 step_id 时用 `tool_name:序号`），去重；
- 沉淀门槛改用"成功工具数"后，该字段仅用于展示与排查。

**自审 grill**

- Q：为什么不直接建 `EvidenceItem` 列表？
  A：改动面覆盖 Agent、记忆、API、前端四层，收益主要是可追溯性；先用低成本的引用标识，等有明确追溯需求再升级。

## 五、验收标准

| 项 | 验收方式 |
| --- | --- |
| 第二轮条件执行 | 无共享发现时事件与日志均无 round=2；有发现时仅一次 |
| 第二轮回退 | 注入"第二轮空结论"的 stub，最终结果等于第一轮 |
| 降级 | 首次网络异常后仍尝试原生调用（重试 1 次）；不支持工具时只降级一次并出现 `agent_degraded` |
| 置信度 | 零成功工具 → ≤0.55；调研全失败 → 显著下降；正常报告与现状同量级 |
| unknown 收敛 | 模型连续输出散文时，≤2 轮后进入强制收敛 |
| 派发去重 | 模型返回重复 Agent 名时，前端工位不重复 |
| 工具超时 | 注入 sleep 超时的 stub 工具，返回 failed 且不阻塞后续 Agent |
| 落盘并发 | 8 线程 × 20 轮压测无异常日志，文件回合数与内存一致 |
| 沉淀 | 低置信度/短结论不写入；写入不阻塞任务完成事件 |
| 多轮 | 同一会话第二次提问携带上一轮资产与摘要；点"新对话"后清空 |

## 六、风险与回滚

- **风险**：第二轮条件化可能让"预期需要交叉验证"的问题少一次补充 → 用 env `AGENT_SUPPLEMENT_MODE=always|conditional|off` 兜底，默认 `conditional`，异常时切 `always`。
- **风险**：置信度公式变化会让历史与新报告不可直接比较 → 在 `answer` 中记录 `confidence_version`，前端不展示版本，仅用于排查。
- **风险**：异步沉淀丢任务 → 单线程队列 + 日志；必要时可临时改回同步（配置项）。
- **回滚方式**：每个阶段独立提交，按 PR 回滚；不涉及数据库迁移，`sessions.json` 结构仅删除字段，向后兼容。

## 七、明确不做

- 不更换 LLM 供应商、不引入 LangGraph 等新编排框架；
- 不新增前端页面与交互（多轮复用现有输入条）；
- 不重写 ReAct 循环；
- 不做多进程部署适配；
- 不在本方案内补自动化测试（按项目约定，需明确要求后再补）。
