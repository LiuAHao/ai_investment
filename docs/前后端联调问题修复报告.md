# 前后端联调问题修复报告

## 1. 背景

针对前后端联调异常，已对项目启动链路、前端页面请求路径、认证信息传递方式以及后端接口可达性进行了实际验证。

本报告基于实际测试结果，整理当前已确认的问题，并给出对应修复方案，用于后续实施和回归验收。

## 2. 已确认问题

### 2.1 后端默认启动端口冲突

后端主程序 `src/api/main.py` 默认监听 `5000` 端口，但测试环境中该端口已被 macOS AirPlay Receiver 占用，导致执行 `python run.py --backend` 时后端无法正常启动。

影响：

- 项目默认启动方式失效。
- 前端即使启动成功，也无法依赖该启动链路完成联调。

### 2.2 前后端默认端口配置不一致

前端 `src/web/src/services/apiClient.js` 与 `src/web/src/services/apiV2Service.js` 默认请求 `http://localhost:5001`，但后端主程序默认监听 `5000`。

影响：

- 前后端默认配置不一致。
- 新环境启动时，即使后端启动成功，前端仍可能请求错误端口。

### 2.3 部分前端页面未走统一 API 客户端

`HistoryView.jsx` 和 `SessionList.jsx` 中直接使用 `fetch('/api/chat/sessions')` 发起请求，没有经过统一的 API 基址配置。

影响：

- 在 Vite 开发环境下，请求会发往前端开发服务器 `5173`。
- 由于当前未配置 `/api` 代理，这类请求不会转发到 Flask 后端。
- 页面表现可能为无数据、加载异常或响应内容不是预期 JSON。

### 2.4 认证 token 键名不一致

统一 API 客户端使用 `auth_token` 作为本地存储键名，但 `HistoryView.jsx` 与 `SessionList.jsx` 读取的是 `token`。

影响：

- 页面无法读取到正确的登录态。
- 即使请求地址修正后，相关接口仍可能因未授权而失败。

## 3. 修复目标

本次问题修复需要达到以下目标：

1. 项目按默认方式可以稳定启动后端。
2. 前端默认请求地址与后端实际监听地址一致。
3. 所有前端接口请求统一走同一套 API 配置。
4. 所有页面使用同一套 token 存储与读取规则。
5. 前后端联调在新环境中具备可复制性，不依赖本机偶然存在的服务实例。

## 4. 修复方案

### 4.1 统一后端监听端口

方案建议二选一，并保持全项目一致：

- 方案 A：将后端默认端口从 `5000` 调整为 `5001`。
- 方案 B：保留后端 `5000`，同时调整前端默认 API 地址为 `http://localhost:5000`。

建议采用方案 A，原因如下：

- 当前前端默认已使用 `5001`，改动面更小。
- 可直接避开 macOS 默认占用 `5000` 的常见冲突。
- 对现有前端代码和联调习惯影响较小。

对应实施项：

- 修改 `src/api/main.py` 中 `app.run(... port=5000 ...)` 的默认端口。
- 若项目中存在依赖固定端口的测试或脚本，同步更新默认值。

### 4.2 统一前端 API 基址配置

需要保证所有前端 API 封装默认指向与后端一致的地址。

对应实施项：

- 统一 `src/web/src/services/apiClient.js` 的 `API_BASE_URL`。
- 统一 `src/web/src/services/apiV2Service.js` 的 `API_BASE_URL`。
- 若使用环境变量 `VITE_API_BASE_URL`，则默认值与后端监听端口保持一致。

推荐规则：

```text
后端默认端口：5001
前端默认基址：http://localhost:5001
环境变量覆盖：VITE_API_BASE_URL
```

### 4.3 消除组件内直连接口

需要将 `HistoryView.jsx` 和 `SessionList.jsx` 中的直接 `fetch('/api/...')` 请求，统一改为调用 `apiClient` 中已有的会话接口封装。

对应实施项：

- 将 `HistoryView.jsx` 中的会话列表请求改为调用统一服务方法。
- 将 `SessionList.jsx` 中的会话列表请求改为调用统一服务方法。
- 后续新增页面不得再直接拼接相对路径访问后端接口。

修复后收益：

- 所有请求自动继承统一基址。
- 统一携带鉴权头。
- 后续若接口域名或端口变更，只需修改一处配置。

### 4.4 统一 token 存储键名

需要将前端登录态读写统一到 `auth_token`。

对应实施项：

- 保持 `apiClient.js` 中 `auth_token` 作为唯一存储键。
- 修正 `HistoryView.jsx` 中对 `token` 的读取。
- 修正 `SessionList.jsx` 中对 `token` 的读取。
- 排查其余前端页面，确保不存在 `token` 与 `auth_token` 混用。

### 4.5 是否引入 Vite 代理

若项目希望允许前端使用相对路径 `/api/...`，则需要在 `vite.config.js` 中增加开发代理配置，将 `/api` 转发到 Flask 服务。

建议：

- 当前项目已经有统一 API 客户端，优先统一走客户端，不依赖代理作为主方案。
- Vite 代理可作为开发环境辅助配置，但不应替代接口调用规范治理。

## 5. 推荐实施顺序

建议按以下顺序修复：

1. 先统一后端默认端口，解决启动失败问题。
2. 再统一前端默认 API 基址，解决默认联调地址不一致问题。
3. 修复 `HistoryView.jsx` 和 `SessionList.jsx` 的请求方式。
4. 修复 token 键名不一致问题。
5. 最后补充开发代理或文档说明，减少后续环境配置成本。

## 6. 回归验证标准

修复完成后，应至少执行以下验证：

### 6.1 启动验证

- 执行 `python run.py --backend`，后端可正常启动且无端口占用报错。
- 执行 `python run.py --frontend` 或 `npm run dev`，前端可正常启动。

### 6.2 接口验证

- 访问 `/api/health` 返回 `200`。
- 访问 `/api/agent/v2/health` 返回 `200`。
- 登录接口返回正常 token。
- 未授权访问用户接口时返回 `401`，授权后返回正常数据。

### 6.3 页面联调验证

- 登录后可正常进入研究页。
- 历史研究页可以正确加载会话列表。
- 研究工作台中的会话列表可以正常展示历史记录。
- 浏览器网络请求中不再出现错误发往 `5173/api/...` 的情况。

### 6.4 配置一致性验证

- 前端默认基址与后端默认端口一致。
- 代码中不再存在 `localStorage.getItem('token')` 的旧写法。
- 代码中不再存在绕过统一 API 客户端的核心业务请求。

## 7. 结论

本次联调问题的根因不是单点故障，而是启动配置、接口调用方式和认证状态管理三个层面的组合问题。

修复时应避免只做单点补丁，而应统一处理以下三类约束：

- 端口与启动配置统一。
- 前端请求入口统一。
- 登录态存储规则统一。

按本报告方案实施后，可以消除当前联调中的主要不确定性，使项目在新环境中具备稳定、可复制的前后端联调能力。
