# AI 投资分析系统 V2 阶段完成度评估

## 1. 评估结论

截至当前阶段，V2 已经从最初的技术设计方案落地为一个可运行、可测试、可演示的多资产投资研究 Agent 原型系统。

整体完成度建议评估为：

```text
总体完成度：约 85% - 88%
面试展示完成度：约 90%
生产化完成度：约 65% - 70%
```

这个判断的核心原因是：

- V2 的主干 Agent 架构已经完成。
- LangGraph 动态编排、资产识别、工具注册、证据池、合规校验、连续追问、自动评测和前端研究工作台都已经具备最小可运行闭环。
- 自动化测试已经覆盖核心模块，后端全量测试通过。
- 前端工作台可以构建通过，并已接入 V2 查询、证据、轨迹、反馈和评测面板。
- 但任务队列、数据源质量、节点级实时事件、数据库迁移、评测集规模和生产可靠性仍未达到真正生产系统标准。

因此，当前版本更准确的定位是：

> V2 已经是一个具备完整 AI Agent 工程能力展示价值的投资研究助手原型，但还不是可以直接面向真实资金决策的生产级投顾系统。

## 2. 已完成内容

### 2.1 V2 基础架构与迁移边界

已完成：

- 新增 `src/agent/v2` 独立目录，不破坏 V1 主链路。
- 新增 V2 状态模型、Schema、图编排、上下文加载、意图识别、资产解析、任务规划、工具执行、证据收集、回答生成、校验、合规和记忆模块。
- 新增 `/api/agent/v2/query`、`/api/agent/v2/status/{task_id}`、`/api/agent/v2/session/{session_id}` 和健康检查接口。
- 通过 `AGENT_V2_ENABLED` 控制 V2 API 注册，保留 V1 可用性。
- V2 异步任务服务支持 `user_id` 绑定，避免任务越权访问。

完成度判断：

```text
完成度：90%
```

未完全完成：

- 当前后台任务仍主要基于内存线程池，不是持久化任务队列。
- 服务重启后任务状态仍会丢失。

### 2.2 LangGraph 动态编排核心

已完成：

- 使用 LangGraph 构建 V2 Agent 执行图。
- 主链路包括：
  - `load_context`
  - `route_intent`
  - `resolve_assets`
  - `plan_tasks`
  - `execute_tools`
  - `collect_evidence`
  - `draft_answer`
  - `critic_check`
  - `compose_answer`
  - `compliance_check`
  - `finalize_answer`
  - `save_memory`
- 已实现关键工具失败后的重新规划逻辑。
- 已实现重规划次数上限，避免无限循环。
- 高风险请求会在规划阶段短路，避免无意义工具调用。

完成度判断：

```text
完成度：88%
```

未完全完成：

- 目前动态编排仍以规则规划为主，ReAct 风格的模型自主规划程度有限。
- 节点级 timeout、retry、fallback 策略还不够细。
- LangGraph 执行过程尚未做到完整节点级 SSE 实时推送。

### 2.3 多资产识别与资产模型

已完成：

- 新增统一资产模型 `Asset` 和资产类型枚举。
- 支持 A 股、美股、基金、ETF、指数、宏观、行业等资产类型建模。
- 新增资产主数据文件。
- 支持代码、名称、别名、ticker、基金代码、ETF 代码识别。
- 支持连续追问中继承上一轮资产上下文。
- 对歧义资产具备候选识别和澄清基础能力。

完成度判断：

```text
完成度：85%
```

未完全完成：

- 港股、宏观、行业的工具链覆盖仍偏弱。
- 资产主数据规模较小，离真实生产覆盖还有距离。
- 歧义资产澄清还没有完整前端交互闭环。

### 2.4 工具注册中心与工具适配器

已完成：

- 新增 `src/tools` 工具体系。
- 新增统一工具规格 `ToolSpec`、工具基类 `BaseTool`、工具结果 `ToolResult`。
- 新增工具注册中心，可按资产类型和意图筛选工具。
- 已接入 A 股行情、新闻搜索、知识库检索、综合分析、基金、ETF、美股等工具。
- 工具结果包含状态、来源、时间、置信度、错误信息、耗时等字段。
- 工具失败会返回标准化失败结果，不再直接打断主链路。

完成度判断：

```text
完成度：86%
```

未完全完成：

- 部分工具仍是对 V1 能力的适配封装，数据质量和字段结构不够统一。
- 美股、ETF、基金等工具仍处于基础可用状态。
- fallback tool 链路还没有完全自动化。

### 2.5 证据池与回答生成链路

已完成：

- 新增 `EvidenceItem` 结构。
- 工具结果可转换为行情、新闻、RAG、分析结论等证据。
- 最终回答包含摘要、关键判断、证据依据、情景分析、主要风险、操作选项、数据限制和风险提示。
- 新增 `EvidenceRecord` 表模型，证据可以入库。
- 回答生成在证据不足时会提示限制，不直接生成确定性结论。
- AnalysisAgent 结果也被纳入证据链。

完成度判断：

```text
完成度：88%
```

未完全完成：

- 证据质量评分仍以规则为主，尚未引入更系统的 faithfulness 检测。

### 2.6 连续追问与记忆系统

- 对话和证据会写入数据库。

## 4. 与原始 V2 目标的差距

### 4.1 最大差距一：任务系统尚未生产化

原方案建议引入：

- Celery
- Redis
- 持久化任务状态
- 重试机制
- 取消机制
- 超时强制终止

当前实现：

- 仍主要使用内存线程池。
- 支持 timeout 状态，但不能强杀底层阻塞任务。
- 服务重启后任务会丢失。

后续建议：

```text
优先级：高
建议阶段：V2.1
```

落地方向：

- 引入 Redis。
- 使用 Celery 管理长任务。
- 将 V2 查询、评测任务、RAG 构建、资产主数据刷新都改为 Celery task。
- 任务状态持久化到数据库。
- 前端通过 task_id 查询持久化状态。

### 4.2 最大差距二：数据源质量不足

当前数据源仍以公开接口和已有 V1 能力为主。

问题：

- 部分数据源不稳定。
- 港股、宏观、行业覆盖不足。
- 财务数据、估值数据、基金持仓、ETF 跟踪误差等还不完整。
- 数据新鲜度和数据来源可信度还没有严格治理。

后续建议：

```text
优先级：高
建议阶段：V2.1 - V2.2
```

落地方向：

- 为每类资产建立标准数据 contract。
- 将数据源适配器拆为 primary、fallback、mock 三层。
- 每个 ToolResult 强制包含 `source`、`observed_at`、`freshness_seconds`、`confidence`。
- 对关键数据建立 freshness gate，过期数据必须在回答中显式提示。

### 4.3 最大差距三：评测集规模和质量不足

当前已有评测系统，但样本规模仍偏小。

问题：

- 评测集还不能覆盖真实用户问题分布。
- 对“答案质量”的自动打分仍偏粗。
- 缺少版本对比、趋势分析和失败样本归因。

后续建议：

```text
优先级：高
建议阶段：V2.1
```

落地方向：

- 将评测集扩展到 100 - 300 条。
- 按资产类型、意图、安全、降级、多轮追问分别建 benchmark。
- 增加 gold answer 或 reference rubric。
- 用户反馈自动转化为候选评测样本。
- 每次核心改动运行 regression eval。

### 4.4 最大差距四：实时可观测仍不够细

当前已经有 trace、tool call 和 SSE 基础，但还没有完整节点级实时事件。

问题：

- 前端可以展示最终 trace，但节点运行过程还不够实时。
- tool_started、tool_completed、evidence_added 等事件还没有完全接到每个节点。
- token 消耗、模型调用耗时、工具调用参数脱敏展示仍可增强。

后续建议：

```text
优先级：中高
建议阶段：V2.2
```

落地方向：

- 给每个 LangGraph 节点加统一 instrumentation wrapper。
- 节点开始、节点结束、工具开始、工具结束、证据新增、合规结果都发送事件。
- 事件进入数据库，前端同时消费 SSE。
- 调试模式展示脱敏后的 trace。

### 4.5 最大差距五：记忆和反馈尚未形成自进化闭环

原方案中提到希望系统能根据用户反馈动态升级。

当前实现：

- 用户反馈可以提交。
- 研究上下文可以保存。
- 评测结果可以记录。

但还没有完成：

- 反馈自动分类。
- 反馈生成评测样本。
- 失败样本驱动 prompt/tool/schema 优化。
- 用户偏好长期建模。

后续建议：

```text
优先级：中
建议阶段：V2.2 - V2.3
```

落地方向：

- 增加 `feedback_queue`。
- 将负反馈自动转化为 eval candidate。
- 引入人工确认后进入正式评测集。
- 建立 prompt version 和 eval run 的关联。
- 对每次系统改动输出 eval diff。

让 V2 从“可演示”提升到“稳定可跑”。

5. 我如何设计自动化评测。
6. 我如何支持连续追问和记忆。
7. 我如何在前端展示 Agent 的执行过程。

推荐表达：

> 这个项目的目标不是替用户做确定性投资决策，而是构建一个可追踪、可评测、可合规约束的投资研究 Agent。V1 是固定多 Agent 流程，V2 则用 LangGraph、Tool Registry、Evidence Store、Critic、Compliance 和 Eval Engine 形成一个更工程化的 Agent 系统。

当被问到“它真的能给投资建议吗”时，建议回答：

> 它可以提供研究辅助和情景分析，但不会输出确定性买卖建议。系统会基于公开数据、新闻和知识库生成分析，并明确风险、数据限制和置信度。为了避免模型幻觉和不合规表达，我引入了证据池、Critic 校验、Compliance 校验和自动化安全评测。

## 7. 最终判断

当前 V2 已经完成了从设计到工程原型的关键跃迁。

已经完成的核心价值：

- 从固定多 Agent 流程升级为 LangGraph 动态编排。
- 从单一 A 股分析扩展到多资产模型。
- 从直接生成答案升级为证据池驱动回答。
- 从无评测升级为自动化评测体系。
- 从一次性分析升级为连续追问与记忆。
- 从普通结果页升级为研究工作台。
- 从简单 demo 升级为具备工程治理意识的 Agent 系统。

仍需继续补强的部分：

- Celery/Redis 任务系统。
- Alembic 数据库迁移。
- 更大规模和更高质量的评测集。
- 更稳定和更丰富的数据源。
- 更完整的节点级实时事件流。
- 反馈驱动的自优化闭环。
- 端到端测试、压力测试和 CI/CD。

综合来看：

```text
如果目标是面试展示 AI Agent 工程能力：当前版本已经基本达标。
如果目标是上线给真实用户长期使用：还需要完成 V2.1 和 V2.2 的工程化补强。
如果目标是辅助真实资金决策：还需要继续增强数据质量、评测体系、合规体系和风险控制。
```
