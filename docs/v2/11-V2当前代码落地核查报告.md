# V2 当前代码落地核查报告

> 基于 `docs/V2技术设计落地方案.md` 与当前仓库代码的静态对照审查
> 生成时间：2026-05-15

## 1. 结论摘要

当前仓库已经实现了 V2 的**核心工作流骨架**，包括：LangGraph 编排、V2 API、资产解析、工具执行、证据池、Critic / Compliance、连续追问基础、评测框架雏形以及前端研究工作台。

但从设计稿和当前前后端真实联调路径看，V2 仍属于**核心骨架已落地、演示链路待加固的 MVP**，尚未达到“设计文档所定义的完整 V2”：

- 动态规划仍偏规则驱动，不是完整 ReAct / 动态规划系统。
- 多资产支持已有基础，但港股、宏观、指数、组合分析工具链仍不完整。
- V2 API 受环境开关控制，默认配置下未启用，前端研究工作台存在默认无法直连 V2 的风险。
- 前端 V2 API 默认端口、偏好字段、SSE 事件协议与后端实现存在主路径契约偏差。
- SSE 事件流和任务状态管理主要停留在任务级，未真正做到节点级、工具级实时过程展示。
- 评测系统已有 runner 和结果展示，但缺少完整的评测启动 API 与后台任务化闭环。
- 任务执行仍基于内存线程池，未达到 Celery/Redis 的持久化队列目标。

**综合判断：**

- 按“代码骨架落地”判断：**约 75% - 85%**
- 按“V2 可演示产品闭环”判断：**约 60% - 70%**
- 可演示性：**有基础，但默认配置和前后端契约需要先修正**
- 生产化程度：**仍需补强**

## 3. 未完全实现或存在偏差的部分

### 3.1 动态规划不够“动态”

设计稿要求的是 ReAct / LangGraph 驱动的动态任务规划，但当前 Planner 仍偏规则和硬编码：

- 按资产类型显式拼装工具
- 按 `requires_news` / `requires_knowledge` 补步骤
- 重新规划主要依赖失败工具

代码位置：`src/agent/v2/planner_agent.py`

**问题：**

- 没有真正做到“根据证据不足自动补查”
- 没有真正做到“模型主导的任务分解”
- 没有完整的条件分支 / 循环补查 / 回退策略

---

### 3.2 多资产覆盖不完整

虽然模型层已经支持多资产，但工具链覆盖仍不均衡：

**已较明确覆盖：**
- A 股
- 美股
- ETF
- 基金

**仍偏弱或未完整实现：**
- 港股
- 指数
- 宏观指标
- 组合 / 持仓分析
- ETF / 基金深度指标（持仓、回撤、跟踪误差、流动性、同类比较）

代码位置：`src/tools/`

---

### 3.3 SSE 过程事件不完整

文档和前端都预期有更细粒度事件：

- `node_started`
- `tool_started`
- `tool_completed`
- `evidence_added`
- `draft_created`
- `critic_completed`
- `compliance_completed`

但当前任务服务实际主要发的是任务级事件：

- `task_started`
- `task_completed`
- `task_failed`
- `node_completed`

代码位置：

- `src/api/events.py`
- `src/services/task_service.py`
- `src/agent/v2/graph.py`
- `src/web/src/services/apiV2Service.js`

**进一步核查：**

- `TaskService.update_task_progress()` 虽然可以发 `node_completed`，但当前 V2 执行链路主要通过 `run_v2_query()` 一次性 `app.invoke()` 执行，未看到节点执行时主动调用该进度更新。
- 前端监听了 `node_started`、`tool_started`、`tool_completed`、`evidence_added`、`draft_created` 等事件，但后端没有对应的实际发射闭环。

**影响：** 前端工作台的过程展示会“有框架、缺细节”；真实运行时更可能是任务开始后等待，最终一次性返回结果，而不是实时展示 Agent / 工具 / 证据流。

---

### 3.4 任务队列仍是内存实现

当前任务执行仍基于 `ThreadPoolExecutor` 和内存态 `_tasks`。

代码位置：`src/services/task_service.py`

**与设计稿差距：**

- 没有 Celery / Redis
- 没有持久化队列
- 服务重启后任务状态丢失
- 没有真正的重试 / 取消 / 恢复机制

---

### 3.5 评测系统缺少启动 API

当前有评测 runner 和结果查询，但缺少完整的“启动评测”接口闭环。

**现状：**
- 有 `GET /api/eval/runs`
- 没有看到 `POST /api/eval/runs`

代码位置：`src/api/eval_api.py`

---

### 3.6 反馈数据模型不够独立

当前反馈写入方式是把反馈塞进 `AnalysisSession.result_summary` JSON。

代码位置：`src/api/feedback.py`

**与设计稿差距：**

- 没有独立 `user_feedback` 表
- 反馈和会话结果耦合较强
- 后续做分析统计不够方便

---

### 3.7 前后端接口契约不完全一致

当前存在几处值得优先修正的契约偏差：

1. 前端提交的偏好字段为 `debugMode`、`riskPref`、`period`，后端读取的是 `debug_mode`、`risk_preference`，投资周期也未形成明确字段契约。
2. 前端监听的 SSE 事件种类多于后端实际发射事件。
3. 前端对结构化结果字段的期望高于当前后端返回。
4. 前端 V2 API 默认请求 `http://localhost:5001`，而项目常见后端启动说明和 Flask 默认端口更接近 `5000`，默认演示路径可能直接请求失败。
5. `.env.example` 中 `AGENT_V2_ENABLED=false`，而主应用只有在该开关为 true 时才注册 V2 API，默认配置下 V2 工作台会打不到 `/api/agent/v2/*`。

代码位置：

- `src/web/src/components/research/ResearchChatView.jsx`
- `src/web/src/services/apiV2Service.js`
- `src/api/agent_v2.py`
- `src/api/events.py`
- `src/api/main.py`
- `.env.example`

**影响：** 这不是单纯的“展示字段不完整”，而是会直接影响 V2 工作台默认可用性和演示稳定性的主路径问题。

## 5. 优先改进建议

### P0：直接影响可用性

1. 统一 V2 开关和启动说明，确保默认演示路径能启用 `/api/agent/v2/*`。
2. 统一前端 `VITE_API_BASE_URL` / 后端端口，避免默认请求 `5001`、后端实际运行在 `5000` 的断链。
3. 统一前后端偏好字段：建议明确为 `debug_mode`、`risk_preference`、`investment_horizon`，或后端兼容当前 camelCase 字段。
4. 补齐 SSE 事件协议，至少打通 `node_started`、`node_completed`、`tool_started`、`tool_completed`、`evidence_added`、`critic_completed`、`compliance_completed`。
5. 统一任务状态 / 会话状态 / 结果状态，并在 V2 API 未启用或请求失败时给前端明确错误态，不要只静默结束分析。

### P1：提升 V2 可信度

1. Planner 已接入 Tool Registry 查询，但仍硬编码资产类型到工具映射；下一步应基于工具 schema / intents / 数据新鲜度做动态选择。
2. Evidence 元数据标准化
3. Critic / Compliance 结构化输出
4. 增强 follow-up 的增量规划

### P1：补齐多资产能力

1. 港股工具链
2. 宏观工具链
3. 指数工具链
4. Portfolio / 持仓分析

### P2：补齐工程闭环

1. `POST /api/eval/runs`
2. 独立 `user_feedback` 表
3. Celery / Redis 任务队列
4. 评测趋势与版本对比

---

## 6. 最终判断

如果按设计稿标准判断，当前 V2 已经不是“未开始”，也不是“只做了文档”，而是：

> **已经完成了 V2 的核心骨架，但可演示闭环仍依赖若干默认配置、前后端契约和事件流问题的修正。**

更适合的定位是：

- **产品展示：可用性有基础，但需要先修 P0**
- **面试演示：有亮点，但需要准备固定环境和演示路径**
- **生产投研：还需继续补强**
