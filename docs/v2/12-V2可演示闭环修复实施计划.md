# V2 可演示闭环修复实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 修复 V2 研究工作台从默认启动、提交查询、实时展示过程到返回结构化结果的主路径问题，让当前 V2 从“核心骨架已落地”推进到“稳定可演示闭环”。

**Architecture:** 本计划优先收敛前后端契约与演示主链路，不引入 Celery / Redis 等重型生产化依赖。短期通过统一配置、字段、SSE 事件和错误态，保证 V2 工作台可用；中期再增强 Planner、Evidence、Critic / Compliance、多资产工具链和评测反馈闭环。

**Tech Stack:** Python、Flask、LangGraph、SQLAlchemy、React、Vite、EventSource、SQLite、AKShare、ChromaDB。

---

## 1. 背景与目标

当前 V2 已经具备 LangGraph 主流程、V2 API、任务服务、事件总线、工具执行、证据池、合规校验、评测 runner 和前端研究工作台。但根据 `docs/v2/11-V2当前代码落地核查报告.md` 的严格核查，V2 的主路径仍存在默认不可用、契约不统一和实时过程展示缺失等问题。

本计划的目标不是一次性把 V2 推到生产级投研系统，而是先完成“可演示闭环”：

- 默认配置或 README 指引下，能明确启动 V2 后端与前端。
- 前端 V2 请求地址与后端实际端口一致。
- 前端提交的偏好字段能被后端正确识别。
- V2 API 未启用、鉴权失败、任务失败时，前端能明确展示错误。
- SSE 至少能展示节点开始、节点完成、工具开始、工具完成、证据生成、校验完成等关键过程。
- 最终结果、证据、工具轨迹、Critic / Compliance 信息能稳定落到前端工作台。

## 2. 当前核心问题

### 2.1 V2 默认启动链路不稳

**现状**

- `.env.example` 中 `AGENT_V2_ENABLED=false`。
- `src/api/main.py` 只有在 `AGENT_V2_ENABLED=true` 时才注册 `agent_v2_bp` 和 `events_bp`。
- 前端研究工作台默认就会调用 `/api/agent/v2/*`。

**影响**

默认环境下，V2 工作台可能直接请求到 404，用户看起来像“分析结束但没有结果”。这会直接影响展示、验收和后续开发调试。

**修改方向**

- 保持生产安全默认值可以继续为 `false`，但必须补齐开发演示配置路径。
- 在前端检测 V2 API 不可用时显示明确错误。
- 在文档和启动脚本中明确 V2 演示需要设置 `AGENT_V2_ENABLED=true`。

### 2.2 前后端端口契约不一致

**现状**

- `src/web/src/services/apiV2Service.js` 默认 `API_BASE_URL` 为 `http://localhost:5001`。
- 当前根 README 常见说明和 Flask 默认习惯更接近 `http://127.0.0.1:5000`。
- `run.py` 没有显式端口传参或统一输出后端 URL。

**影响**

即使后端正常启动，前端仍可能请求错误端口。这个问题比业务逻辑问题更靠前，会让演示链路直接断掉。

**修改方向**

- 统一默认后端端口，建议短期统一为 `http://localhost:5000`。
- 前端使用同一个环境变量 `VITE_API_BASE_URL`，并在 `.env.example` 或前端示例配置中写清楚。
- 后端启动日志输出实际端口和 V2 是否启用。

### 2.3 偏好字段不匹配

**现状**

- 前端提交：`debugMode`、`riskPref`、`period`。
- 后端读取：`debug_mode`、`risk_preference`。
- 投资周期没有明确字段契约。

**影响**

用户在前端选择风险偏好、投资周期、调试模式后，后端不一定使用这些信息，导致结果与界面设置脱节。

**修改方向**

- 建议统一请求字段为：
  - `debug_mode`
  - `risk_preference`
  - `investment_horizon`
- 后端短期兼容旧字段：
  - `debugMode` -> `debug_mode`
  - `riskPref` -> `risk_preference`
  - `period` -> `investment_horizon`
- 后续前端改为只提交 snake_case 字段。

### 2.4 SSE 事件协议未真正打通

**现状**

- 前端监听 `node_started`、`node_completed`、`tool_started`、`tool_completed`、`evidence_added`、`draft_created`、`critic_completed`、`compliance_completed` 等事件。
- 后端事件总线具备发布能力。
- `TaskService` 实际主要发 `task_started`、`task_completed`、`task_failed`。
- `TaskService.update_task_progress()` 可发 `node_completed`，但 V2 图执行链路没有稳定调用。

**影响**

前端流程画布有 UI 框架，但真实运行时更像“开始等待，结束后一次性展示结果”，不能体现 V2 的过程可视化价值。

**修改方向**

- 在 `run_v2_query()` 或 LangGraph 节点外层加入事件回调能力。
- 短期可在各节点函数返回 trace 后补发事件；更理想的是在节点开始前、结束后分别发事件。
- 工具执行器在每个工具调用前后发 `tool_started` / `tool_completed`。
- 证据池生成时发 `evidence_added`。
- Critic / Compliance 节点完成时发对应事件。

### 2.5 前端错误态过弱

**现状**

- `ResearchChatView.jsx` 在提交失败、轮询失败、任务失败时大多只是 `setPhase('done')`。
- 页面没有保留错误信息，也没有提示 V2 未启用、鉴权失败、额度耗尽、后端不可达等具体原因。

**影响**

用户无法判断问题来自配置、网络、鉴权、后端异常还是业务执行失败。开发阶段也会增加排查成本。

**修改方向**

- 增加 `errorMessage` 状态。
- 提交失败、SSE 错误、轮询失败、任务失败时展示明确错误。
- 对常见错误做友好提示：
  - V2 未启用
  - 未授权或登录过期
  - 今日额度已用完
  - 后端服务不可达
  - 任务超时

## 4. 分阶段执行计划

### 阶段一：修复默认可用性与 API 契约

**目标**

让前端能稳定请求正确的 V2 后端，并让用户在前端选择的偏好进入后端。

**问题 1：前端默认 API 地址与后端不一致**

修改方向：

- 将 `src/web/src/services/apiV2Service.js` 的默认值从 `http://localhost:5001` 调整为 `http://localhost:5000`。
- 保留 `import.meta.env.VITE_API_BASE_URL` 作为优先配置。
- 后续如项目决定固定使用 `5001`，则反向修改后端启动端口和文档；关键是只能有一个默认口径。

涉及文件：

- `src/web/src/services/apiV2Service.js`
- `.env.example`
- `README.md`（后续 README 重写时处理）

验收标准：

- 未设置 `VITE_API_BASE_URL` 时，前端请求 `http://localhost:5000/api/agent/v2/health`。
- 设置 `VITE_API_BASE_URL=http://localhost:5001` 时，前端请求 `5001`。
- 浏览器网络面板中 V2 请求地址和后端实际地址一致。

**问题 2：V2 默认未启用导致工作台不可用**

修改方向：

- 不建议为了演示直接把生产默认值改成 true。
- 建议增加明确开发演示配置：
  - `.env.example` 保持 `AGENT_V2_ENABLED=false`，但增加注释：演示 V2 工作台时设置为 true。
  - 前端在收到 `V2 功能未开启` 或 404 时展示明确提示。
- 后端 `/api/agent/v2/health` 当前也受蓝图注册控制；若 V2 未启用，health 路由不存在。可考虑增加一个不受 V2 开关控制的全局能力状态接口，或在前端将 404 解释为 V2 未启用。

涉及文件：

- `.env.example`
- `src/api/main.py`
- `src/web/src/components/research/ResearchChatView.jsx`
- `src/web/src/services/apiV2Service.js`

验收标准：

- `AGENT_V2_ENABLED=false` 时，前端明确展示“V2 功能未启用，请设置 AGENT_V2_ENABLED=true 并重启后端”。
- `AGENT_V2_ENABLED=true` 时，`/api/agent/v2/query` 可以正常提交任务。

**问题 3：偏好字段不匹配**

修改方向：

- 前端提交字段改为：

```json
{
  "debug_mode": true,
  "risk_preference": "稳健型",
  "investment_horizon": "三个月"
}
```

- 后端兼容旧字段：

```python
debug_mode = preferences.get("debug_mode", preferences.get("debugMode", False))
risk_preference = preferences.get("risk_preference", preferences.get("riskPref"))
investment_horizon = preferences.get("investment_horizon", preferences.get("period"))
```

- `user_profile` 中统一使用标准字段。

涉及文件：

- `src/web/src/components/research/ResearchChatView.jsx`
- `src/api/agent_v2.py`

验收标准：

- 前端选择“激进型”“一年”“调试模式开启”后，后端 `user_profile` 中存在：
  - `risk_preference="激进型"`
  - `investment_horizon="一年"`
  - `debug_mode=True`
- 旧字段请求仍可被后端兼容。

### 阶段二：补齐前端错误态

**目标**

用户能知道任务为什么失败，而不是看到空白或静默结束。

**问题：失败路径没有明确 UI 状态**

修改方向：

- 在 `ResearchChatView.jsx` 增加：

```jsx
const [errorMessage, setErrorMessage] = useState('');
```

- 提交分析前清空错误：

```jsx
setErrorMessage('');
```

- `catch (err)` 中设置错误：

```jsx
setErrorMessage(err?.message || '分析请求失败，请检查后端服务是否启动');
setPhase('done');
```

- `task_failed` 事件中读取后端错误：

```jsx
setErrorMessage(event.data?.error || '任务执行失败');
```

- 轮询失败时设置：

```jsx
setErrorMessage('无法获取任务状态，请检查网络或后端服务');
```

涉及文件：

- `src/web/src/components/research/ResearchChatView.jsx`
- `src/web/src/services/apiV2Service.js`

验收标准：

- 后端未启动时，前端显示“后端服务不可达”或等价提示。
- V2 未启用时，前端显示 V2 未启用提示。
- 任务超时时，前端显示任务超时提示。
- 任务失败时，前端展示后端返回的 error。

### 阶段三：打通 SSE 过程事件

**目标**

让研究工作台从“最终结果展示”升级为“过程可视化展示”。

**事件协议**

建议短期固定如下事件结构：

```json
{
  "type": "node_started",
  "task_id": "xxx",
  "timestamp": 1234567890,
  "data": {
    "node": "plan_tasks",
    "label": "任务规划"
  }
}
```

```json
{
  "type": "node_completed",
  "task_id": "xxx",
  "timestamp": 1234567890,
  "data": {
    "node": "plan_tasks",
    "status": "completed",
    "latency_ms": 123,
    "summary": "planned 4 steps"
  }
}
```

```json
{
  "type": "tool_started",
  "task_id": "xxx",
  "timestamp": 1234567890,
  "data": {
    "tool_name": "cn_stock_history",
    "step_id": "cn_stock_history_0",
    "description": "获取 A 股历史行情"
  }
}
```

```json
{
  "type": "tool_completed",
  "task_id": "xxx",
  "timestamp": 1234567890,
  "data": {
    "tool_name": "cn_stock_history",
    "step_id": "cn_stock_history_0",
    "status": "success",
    "latency_ms": 523,
    "result": {
      "summary": "获取历史行情成功"
    }
  }
}
```

```json
{
  "type": "evidence_added",
  "task_id": "xxx",
  "timestamp": 1234567890,
  "data": {
    "evidence": {
      "evidence_type": "market_data",
      "title": "行情证据",
      "summary": "近三个月涨跌幅..."
    }
  }
}
```

**后端修改方向**

- `TaskService` 增加公开事件发送封装，例如：

```python
@classmethod
def emit_event(cls, task_id: str, event_type: str, data: Dict[str, Any] = None) -> None:
    _emit_task_event(task_id, event_type, data or {})
```

- `agent_v2.py` 提交任务时，将 `task_id` 传给 `run_v2_query()`。

```python
result = run_v2_query(
    session_id=session_id,
    user_id=user.id,
    query=query_text,
    chat_history=chat_history,
    user_profile=user_profile,
    task_id=task_id,
)
```

- `graph.py` 的 `run_v2_query()` 接收 `task_id: Optional[str] = None`。

- 短期实现方式：
  - 在每个节点函数中不侵入业务逻辑，只在图执行前后包一层事件发送较难。
  - 更务实的方式是先在各关键节点内部发送事件。
  - 对于 `execute_tools`，必须在工具执行前后发事件，因为这是前端工具卡片的主要数据来源。

涉及文件：

- `src/services/task_service.py`
- `src/api/agent_v2.py`
- `src/agent/v2/graph.py`
- `src/agent/v2/executor.py`
- `src/agent/v2/evidence_agent.py`
- `src/agent/v2/critic_agent.py`
- `src/agent/v2/compliance_agent.py`
- `src/web/src/services/apiV2Service.js`
- `src/web/src/components/research/ResearchChatView.jsx`

验收标准：

- 提交一次 V2 查询后，浏览器 EventSource 能依次收到：
  - `task_started`
  - 至少 3 个 `node_started`
  - 至少 3 个 `node_completed`
  - 至少 1 个 `tool_started`
  - 至少 1 个 `tool_completed`
  - `task_completed`
- 前端流程画布能看到节点从等待到运行中再到已完成。
- 工具卡片能显示工具运行和完成状态。
- SSE 发送失败不会中断 V2 主流程。

### 阶段四：统一最终结果与前端展示

**目标**

保证最终结果、证据、工具结果和校验信息都能被前端稳定消费。

**问题：前端对结构化结果期望高于后端返回**

修改方向：

- 后端结果保持以下字段稳定：

```json
{
  "session_id": "xxx",
  "final_answer": "string",
  "investment_answer": {},
  "degraded": false,
  "errors": [],
  "trace": [],
  "assets": [],
  "evidence_items": [],
  "tool_results": [],
  "critic_result": {},
  "compliance_result": {}
}
```

- 如果 Critic / Compliance 当前只在 state 内部存在，应在 `run_v2_query()` 最终 result 中显式导出。
- 前端优先渲染 `investment_answer`，缺失时回退 `final_answer`。
- 工具轨迹优先使用 SSE 过程事件，任务完成后用 `tool_results` 做补全。

涉及文件：

- `src/agent/v2/graph.py`
- `src/agent/v2/state.py`
- `src/web/src/components/research/ResearchChatView.jsx`

验收标准：

- 一次成功分析后，前端至少展示：
  - 最终摘要
  - 风险提示
  - 行动选项或结论
  - 证据列表
  - 工具轨迹
- 后端降级时，前端能展示 `degraded` 和 `errors`。

### 阶段五：Planner 与 Tool Registry 改进

**目标**

让 Planner 从“硬编码工具拼装”逐步过渡到“基于工具元数据的选择”。

**现状**

Planner 已经调用 Tool Registry，但仍然按资产类型硬编码：

- A 股 -> `cn_stock_history`
- 美股 -> `us_stock_quote` + `us_stock_history`
- ETF -> `etf_profile` + `etf_tracking_index`
- 基金 -> `fund_profile` + `fund_nav_history`

**修改方向**

- 保留现有规则作为 fallback。
- 使用 `registry.find_tools(asset_type=..., intent=...)` 作为优先工具选择来源。
- 每个工具的 `ToolSpec` 需要补齐：
  - `asset_types`
  - `intents`
  - `freshness_requirement_seconds`
  - `description`
- Planner 输出中记录选择原因：

```python
ExecutionStep(
    step_id="cn_stock_history_0",
    tool_name="cn_stock_history",
    params={"symbol": asset.symbol},
    metadata={"reason": "matched asset_type=cn_stock intent=market_analysis"}
)
```

如果当前 `ExecutionStep` 没有 `metadata` 字段，可先不改模型，只把 reason 写入 trace。

涉及文件：

- `src/agent/v2/planner_agent.py`
- `src/tools/base.py`
- `src/tools/registry.py`
- `src/tools/*_tools.py`

验收标准：

- 对 A 股、美股、ETF、基金查询，Planner 能从 registry 找到候选工具。
- 当 registry 没有匹配工具时，Planner 给出 trace 说明，而不是静默跳过。
- 现有 A 股、美股、ETF、基金链路不回退。

### 阶段六：多资产能力补齐的最小切片

**目标**

先补“能识别但不能分析”的断层，而不是一次性补完全部投研工具。

**优先级**

1. 港股基础行情工具
2. 指数基础行情工具
3. 宏观指标查询工具
4. 组合 / 持仓分析工具

**港股问题**

现状：

- `asset_resolver.py` 可以识别港股代码。
- `tools/registry.py` 未注册港股工具。
- Planner 没有港股资产类型分支。

修改方向：

- 新增 `src/tools/hk_stock_tools.py`。
- 注册 `hk_stock_quote` 或 `hk_stock_history`。
- Planner 增加 `AssetType.HK_STOCK` 分支。
- Evidence Agent 增加港股工具结果转证据。

验收标准：

- 查询 `HK00700` 或 `00700.HK` 时，资产类型为 `hk_stock`。
- Planner 至少生成一个港股工具步骤。
- 工具不可用时返回 `partial` 或明确错误，不影响最终回答生成。

**指数与宏观问题**

修改方向：

- 指数先支持基础指数行情，不追求完整行业归因。
- 宏观先支持少量固定指标，不做完整宏观数据库。
- 工具输出统一转换成 EvidenceItem。

验收标准：

- 查询“沪深300最近走势”能识别为指数或至少触发指数相关工具。
- 查询“近期宏观利率变化对A股影响”能触发宏观或知识检索工具，不再完全依赖通用分析。


验收重点：

- V2 工作台无 lint 错误。
- 构建通过。
- 失败态和成功态都能正常渲染。

### 5.3 联调验证

建议流程：

1. 设置 `AGENT_V2_ENABLED=true`。
2. 启动后端。
3. 启动前端。
4. 登录用户。
5. 进入研究工作台。
6. 提交问题：`分析宁德时代未来三个月的风险`。
7. 观察 EventSource 事件。
8. 观察流程画布状态变化。
9. 等待最终结果展示。
10. 切换后端 V2 关闭或停止后端，确认前端错误态明确。

通过标准：

- 正常链路能完成一次分析。
- 异常链路能展示明确错误。
- 前端不再静默进入空结果状态。

## 7. 风险与取舍

### 7.1 不引入 Celery / Redis 的原因

当前最大问题是演示主路径不稳，而不是后台任务承载能力不足。此阶段继续使用内存线程池，可以更快修复前后端契约和事件可视化。Celery / Redis 应作为 P2 工程化任务单独规划。

### 7.2 不立即重构完整 ReAct Planner 的原因

Planner 动态性不足是事实，但它不是当前演示断链的第一原因。先让现有规则 Planner 的过程和结果稳定可见，再逐步把硬编码映射替换为 Tool Registry 元数据选择。

### 7.3 不一次性补齐所有资产工具的原因

多资产工具链范围很大。短期优先补“已能识别但没有工具”的港股断层，再按指数、宏观、组合逐步推进。

## 8. 完成定义

本计划完成后，V2 应达到以下状态：

- 默认开发演示配置清晰。
- 前端能连接正确后端地址。
- V2 未启用或后端不可用时有明确错误。
- 用户偏好字段能进入后端分析上下文。
- SSE 至少能驱动主要节点和工具状态变化。
- 最终结构化结果能稳定展示。
- 现有 V2 核心测试和前端构建通过。

达到以上标准后，`docs/v2/11-V2当前代码落地核查报告.md` 中的“V2 可演示产品闭环”完成度可以从 **60% - 70%** 上调到 **75% - 85%**；剩余差距主要来自动态 Planner、多资产工具链、评测启动闭环、反馈数据模型和生产级任务队列。
