## 第一部分：Grilling 决策记录

格式：**拷问 → 选项 → 定案 → 理由 → 影响**。共 24 条，按主题分组。

### A. 定位与范围

#### A1. 系统到底交付什么？

- 选项：① 研报辅助（只给分析） ② 交易信号（给买卖与仓位） ③ 持仓跟踪（重复盘与结算）
- **定案：① + ②的弱形态。输出「方向判断 + 置信度 + 仓位区间 + 触发条件」，不输出确定性买卖指令，不接交易。**
- 理由：用户要"投资方向的推荐和判断"。给确定性指令会让系统承担它承担不了的责任（LLM 结论不可复现、数据有延迟），且违反合规边界。仓位区间 + 触发条件既可用又可审计。
- 影响：`Verdict.position_hint` 只允许区间表述；Verifier 词表拦截"满仓/清仓/必涨"等。

#### A2. "功能越多越好"如何避免范围爆炸？

- 选项：① 一次性全做 ② 核心闭环 + 插件式扩展 ③ 按用户临时需求逐个加
- **定案：②。核心闭环固定 6 层，扩展只允许通过三个注册点接入：分析师注册表、工具注册表、知识卡。**
- 理由：范围爆炸的真实代价不是开发时间，是每个新能力都会稀释 prompt 与验收标准。注册点约束能让扩展"加一个不坏一片"。
- 影响：新增 `src/analysts/registry.py`，`AnalystSpec` 含 `name / evidence_categories / tool_names / system_prompt / knowledge_card / budget`。`pipeline.py` 只读注册表，不硬编码分析师名单。

#### A3. 用户规模与并发

- 选项：① 单人本地 ② 小团队多 worker ③ 对外服务
- **定案：①。单 worker，进程内状态，不做任务队列，不做登录。**
- 理由：现有 event_bus / memory / task 都是进程内单例。多 worker 会让 SSE 与执行分属不同进程，必须换 Redis。现在没有这个需求。
- 影响：README 明确写"单 worker 部署"。未来扩展时再换 transport，不改编排层。

#### A4. 是否保留"按需调度"？

- 选项：① 全部 4 路必跑 ② LLM 自由决定 ③ 规则 + LLM 混合
- **定案：③。规则先定下限（涉及个股必跑 Market + Fundamental；有事件关键词加 News；宏观/指数问题加 Macro），LLM 只做"加派"与"跳过理由"。**
- 理由：纯 LLM 派发会出现"该查财务却没派"的静默漏检（现状 `orchestrator.py:355` 已经有静默跳过问题）。规则保底，LLM 补充。
- 影响：`ResearchPlan` 增加 `required_analysts`（规则产出，不可被 LLM 删除）与 `optional_analysts`（LLM 决定）。

### B. 架构

#### B1. 是否引入 LangGraph / AutoGen？

- **定案：不引入。**
- 理由：瓶颈在信息结构不在编排能力。现有同步线程池 + ReAct 已够。LangGraph 的 checkpoint 价值可以用 SQLite 幂等替代（阶段完成即写 `stage_state`）。
- 影响：`pipeline.py` 自己实现阶段状态机与幂等，约 150 行。

#### B2. 分析师之间到底能不能互相看见？

- 选项：① 完全隔离 ② 共享证据、独立判断 ③ 完全共享（含中间结论）
- **定案：②。Ledger 只读共享，分析师能看到"已有哪些证据/哪些问题已被谁回答"，但看不到其他人的判断与 gaps 评价。**
- 理由：完全隔离会导致重复调用同一工具（现状三路各查一次行情）；完全共享会互相锚定，退化成"一个 Agent 写四遍"。共享事实、隔离判断是唯一不损失信息增量又省成本的做法。
- 影响：Ledger 提供 `get_by_category()` 与 `answered_questions()`；`pipeline` 在派发前预填一个"已覆盖清单"。

#### B3. 辩论总是开吗？

- 选项：① 总是 ② 从不 ③ 争议度触发 + 用户强制
- **定案：③。触发条件（任一）：多空证据数量差距 ≤ 1；新闻情绪与价格方向背离；估值分位与增速矛盾；Verifier 在取证阶段报告 `needs_debate=true`。用户可强制开/关。**
- 理由：辩论是成本最高、增量最不确定的一层。无争议时开辩论只会产出"双方都承认对方有道理"的表演。
- 影响：`ResearchPlan.debate` 由规则计算，LLM 不能擅自打开（只能建议）。

#### B4. 风险是否独立成 Agent？

- 选项：① 独立 RiskAgent ② 并入 Verifier + Verdict ③ 并入辩论（第三方）
- **定案：②。风险由 Verifier 的"负面证据覆盖检查" + Verdict 的 `structured_risks` 字段承担。**
- 理由：独立 RiskAgent 在只有 4 路证据的情况下，产出大概率是"政策风险、市场风险、流动性风险"的复述，没有增量。风险的价值在于"这条具体证据是否被定价"，这必须贴着证据做。
- 影响：不新增 Agent；Verifier 增加 `negative_evidence_coverage` 检查（Ledger 中负面证据数 vs Verdict 风险条目数）。

#### B5. 是否做组合层（多资产仓位分配）？

- 选项：① 现在就做 ② 只做对比不做组合 ③ 预留接口
- **定案：②现在做对比结论；③为组合层预留数据结构（`DecisionRecord.portfolio_id` 与 `weight_hint`），不实现优化器。**
- 理由：组合优化（均值方差 / 风险平价）是独立工程，且需要相关性估计与约束求解。先做单资产与多资产对比，价值已经足够。
- 影响：`DecisionRecord` 加字段，`pipeline` 不实现组合求解。

#### B6. 是否需要"补派分析师"？

- **定案：需要，但只在 Verifier 判定"关键问题未答"时，最多补派 1 次，复用原分析师工具白名单，预算单独计。**
- 理由：这是唯一合理的动态拓扑。但必须限额，否则会变成无限重试。
- 影响：`pipeline.repair_dispatch()`，`Budget.repair_calls = 1`。

### C. 回测（用户新增需求）

#### C1. 回测的目的是什么？

- 选项：① 证明系统能赚钱 ② 给系统提供参照与校准 ③ 对外展示业绩
- **定案：②。回测产出三个东西：置信度校准、辩论增量、分析师贡献。不产出"年化收益 X%"作为卖点。**
- 理由：LLM 非确定性 + 新闻历史数据不可得，任何"回测收益率"都不具备可复现性。作为内部参照才有意义。
- 影响：回测报告的主指标是 Brier score、分桶命中率、有/无辩论的差值，而不是累计收益。收益只作辅助列。

#### C2. 做哪种回测？

- 选项：① 只有前向跟踪 ② 只有历史 walk-forward ③ 两者都做
- **定案：③。前向跟踪为主（可信），历史 walk-forward 为辅（快速攒样本），并明确标注后者在新闻类证据上的不可用性。**
- 理由：前向跟踪样本积累慢（一周一个点）；历史回测能快速验证框架逻辑，但只能回测行情/估值/财务三类证据。
- 影响：`src/backtest/` 与 `src/memory/settlement.py` 共用结算逻辑，但数据源不同（前向用实时接口，回测用 PIT 快照）。

#### C3. 如何防未来函数？

- **定案：代码层强制，不靠 prompt。所有工具调用必须带 `as_of`；数据层在返回前过滤 `source_time > as_of` 的记录；财务数据用 `ann_date`（公告日）而非报告期过滤；若某接口无公告日字段，该接口在回测模式下禁用。**
- 理由：LLM 无法可靠地"记住不要用未来数据"。这必须是数据层不变量。
- 影响：`BaseTool.execute` 增加 `as_of` 参数；`tushare_client` 所有方法支持 `as_of` 过滤；回测模式通过环境变量 `PIT_MODE=1` 全局开启。

#### C4. 幸存者偏差怎么处理？

- **定案：资产池用 `index_weight` 的历史成分股，不用当前成分。没有历史成分数据的指数，回测时明确标注 `universe_bias=true`，该批结果不进入统计汇总。**
- 理由：用当前存活股票回测，任何策略都会好看。这是最常见的自欺。
- 影响：`backtest/universe.py` 负责按 as_of 取成分；报告头部展示偏差标记。

#### C5. 样本量与成本怎么控制？

- **定案：pilot 阶段 20-30 个决策点，正式统计 ≥ 100 个决策点且至少覆盖 2 种市场状态。单次决策约 20-25 次 LLM 调用，100 点 ≈ 2000-2500 次调用。因此回测默认使用快模型，且支持 LLM 响应缓存（按输入 hash）以支持重跑。**
- 理由：不回测成本就上线，等于不知道系统在什么情况下会错。
- 影响：`backtest/cache.py`（输入 hash → 响应），`config.backtest_llm_tier = "quick"`。

#### C6. LLM 非确定性怎么处理？

- **定案：同一决策点跑 3 次，报告取多数 stance，并记录 stance 方差与 conviction 方差。方差超过阈值（stance 不一致 ≥ 2/3）的样本单独标记为 `unstable`，不计入核心指标。**
- 理由：不稳定的判断本身就是一个重要信号——说明该情形下证据不足。
- 影响：回测报告增加 `stability` 列。

#### C7. 回测成交与收益怎么算？

- **定案：T 日收盘后决策 → T+1 开盘成交（无法成交则顺延，如涨停/停牌）；收益按前复权价计算；持有期 5 / 20 / 60 交易日三档；基准按资产类型选（A 股用沪深 300，美股用标普 500，ETF 用跟踪指数）。**
- 理由：用当日收盘价决策又当日成交是典型未来函数；用不复权价会在分红送转处产生假信号。
- 影响：`backtest/clock.py` 统一处理交易日历、停牌、涨跌停、复权。

#### C8. 回测输出什么？

- **定案：一份 JSON + 一张前端表格。字段：`decision_id / as_of / stance / conviction / ret_5d / ret_20d / ret_60d / alpha / benchmark / hit / unstable`。汇总：分 stance 命中率、按 conviction 分桶的命中率与 Brier score、有/无辩论的命中率差、单分析师 ablation 的影响。**
- 理由：这些才是"参照"。
- 影响：新增 `backtest/report.py` 与前端 `BacktestView`（P2）。

### D. 数据与工程

#### D1. tushare 权限不确定，怎么办？

- **定案：写 capability probe。启动时探测各接口可用性，缓存到 `src/data/capabilities.json`；不可用接口自动走 akshare 降级；报告中标注每个证据的实际数据源。**
- 理由：权限是外部约束，代码不能假设。硬编码假设会在换账号时静默失败。
- 影响：`src/data/probe.py`；`ToolResult` 增加 `data_source` 字段（tushare / akshare / web）。

#### D2. 财务数据到底走哪个接口？

- **定案：tushare 优先（`income` / `balancesheet` / `cashflow` / `fina_indicator` / `daily_basic`），不可用时 akshare 兜底（`stock_financial_abstract` / `stock_financial_analysis_indicator`）。**
- 理由：tushare 字段规范、有 `ann_date`（回测必需）；akshare 免费但字段口径不统一，只作降级。
- 影响：`financial_tools.py` 内部做源选择，上层工具名不变。

#### D3. 新闻数据源？

- **定案：tushare `news` 优先（若权限可用）→ 东财/新浪网页 → ddgs 兜底。必须返回 `published_at`；无发布时间的搜索结果降权 50% 且不得作为核心论据。**
- 理由：没有发布时间的新闻无法判断时效，也无法回测。
- 影响：`news_client.py` 多源重构；证据模型加 `source_time` 必填校验（缺失则 confidence 降级）。

#### D4. 决策库用什么？

- **定案：SQLite（`src/data/decisions.sqlite`）+ JSONL 导出。**
- 理由：需要按资产/时间/置信度查询，需要事务，需要结算扫描。纯 JSON 做这些很别扭。
- 影响：`memory/decision_store.py` 用标准库 `sqlite3`，不引 ORM。

#### D5. 是否写测试？

- 选项：① 不写 ② 全写 ③ 只测纯逻辑
- **定案：③。新建 `tests/`，只覆盖四个无 LLM 依赖的模块：`ledger`（去重/引用）、`verifier`（机械校验）、`settlement`（收益与 alpha 计算）、`backtest/clock`（T+1 与停牌处理）。LLM 相关路径靠端到端用例人工验收。**
- 理由：这四个模块出错会导致"系统性错误但看起来正常"（引用错、结算错、成交错），是最贵的 bug。LLM 路径的测试脆弱且维护成本高。
- 影响：需建 `tests/` 目录（AGENTS.md 要求有专门测试目录才写测试）。

#### D6. 观测性？

- **定案：每次任务写 `trace.json`：每阶段耗时、LLM 调用数、token 数、工具失败率、各阶段降级原因。任务结束写入 SQLite 的 `traces` 表。**
- 理由：不量化成本与失败率，就无法优化，也无法判断"某次结论质量差"是数据问题还是模型问题。
- 影响：`pipeline.py` 内置 `Trace` 对象，随事件一起发射 `phase_completed`。

#### D7. 前端改多少？

- **定案：渐进式。保留现有 SSE 骨架与 AgentCard，新增 `EvidencePanel`、`DebateTimeline`、`VerdictCard`，删除 round1/round2 状态机。回测页放 P2。**
- 理由：前端已经做过一次重构，再推倒重来收益低。
- 影响：`useAgentStream.js` 去掉 round 逻辑，增加 stage 与 evidence 状态。

### E. 风险与失败模式

#### E1. 本系统最大的失败模式是什么？

- **定案：不是"结论错"，是"结论看起来严谨但实际没有信息增量"。**
- 量化检测：`evidence_citation_density`（每千字结论引用的 evidence 数）、`claim_coverage`（focus_questions 被回答比例）、`debate_increment`（辩论后 claim 变更率）。三者任一低于阈值 → 报告标注"低增量"。
- 理由：投研系统最危险的状态是让用户过度信任。宁可显式说"本次没有增量"。

#### E2. 合规边界？

- **定案：禁止确定性买卖指令、禁止收益承诺、禁止目标价。允许方向判断、估值区间、仓位区间、触发条件。Verifier 词表阻断 + 报告固定免责声明。**
- 理由：这是产品底线，不是可选项。

#### E3. 如果 LLM 服务不可用？

- **定案：任务级降级，返回已完成的阶段结果 + `degraded=true`，不伪造结论。**
- 理由：现状 `loop.py:400` 把 LLM 异常伪装成 final 结论，这是最危险的实现细节，必须删掉。

## 第二部分：功能路线图（回答"功能越多越好"）

插件化之后，扩展 = 注册一个分析师或一个工具。按价值排序：

### P0 核心闭环（必须）

| 能力 | 形态 |
|---|---|
| 单资产研究 | 4 分析师 + 辩论 + 裁决 + 质检 |
| 多资产对比 | 同一 Ledger 多 asset_id，Bull/Bear 按资产分别建论 |
| 方向判断 + 仓位区间 + 触发条件 | Verdict |
| 决策落库与前向结算 | DecisionRecord + Settlement |
| 证据可追溯 | EvidencePanel |

### P1 高价值扩展

| 能力 | 新增内容 | 依赖 |
|---|---|---|
| 财务报表与公告分析 | `FundamentalAnalyst` 工具补齐 + `AnnouncementAnalyst` | tushare/akshare 财务与公告接口 |
| 事件驱动 | 公告/财报日历 → 自动触发研究 | `stock_notice_report`、`disclosure_date` |
| 同业对比与估值分位 | `stock_peer_compare` 工具 | 行业分类 + 全市场估值扫描 |
| 自选股定时跟踪 | 定时器 + 只跑 Market/News + falsifier 检查 | 无需新数据 |
| 预警 | 决策的 `falsifiers_to_watch` 命中时推送 | 结算/监控任务 |
| 组合视角 | 多资产 DecisionRecord 汇总，不做优化器 | 已有多资产能力 |

### P2 扩展

| 能力 | 说明 |
|---|---|
| 行业轮动 | 以行业指数为资产，宏观看景气 + 资金 |
| 资金面分析师 | 主力净流入、龙虎榜、北向（`moneyflow`） |
| 回测平台化 | 参数网格、批量决策点、报告对比 |
| 因子暴露 | 用 tushare 因子数据做风格归因 |
| 组合优化 | 均值方差 / 风险平价（独立模块） |

每个扩展的硬性要求：自带 1 个验收用例 + 1 段知识卡 + 明确的证据类别。没有验收用例的扩展不合并。

## 第三部分：回测系统设计

### 1. 定位

回测不是收益证明，是**系统校准器**。回答三个问题：

1. 系统说"高置信度"的时候，真的更准吗？（置信度校准）
2. 辩论到底有没有带来增量？（ablation）
3. 哪个分析师在贡献信息，哪个在凑数？（贡献度）

### 2. 三种运行模式

| 模式 | 时间推进 | 数据 | 可信度 | 用途 |
|---|---|---|---|---|
| `live` 前向跟踪 | 真实时间 | 实时接口 | 高 | 长期校准，主路径 |
| `walkforward` 历史回测 | 历史 as_of | PIT 快照 | 中（新闻不可用） | 快速攒样本 |
| `ablation` 消融 | 同 walkforward | 同左 | 中 | 归因分析 |

同一套 `pipeline`，只换 `Clock` 与 `DataSource`。编排逻辑不分叉——这是回测有意义的前提。

### 3. 数据可用性分层（决定回测能测什么）

| 证据层 | tushare 接口 | PIT 可行性 | 回测可用 |
|---|---|---|---|
| 行情 | `daily` / `pro_bar` / `index_daily` / `fund_daily` | 有 `trade_date`，完全可行 | 是 |
| 估值 | `daily_basic` / `index_dailybasic` | 有 `trade_date` | 是 |
| 财务 | `income` / `balancesheet` / `cashflow` / `fina_indicator` | 有 `ann_date` / `f_ann_date`，按公告日过滤 | 是（必须按 ann_date） |
| 指数成分 | `index_weight` | 有 `trade_date` | 是 |
| 公告 | `anns_d`（视权限） | 有公告日 | 视权限 |
| 新闻 | `news`（视权限） | 有 `datetime`，但历史覆盖不全 | 视权限，默认标记不可用 |
| 网页搜索 | ddgs | 无法 PIT | **否，回测中禁用** |

规则：回测中任何工具若无法 PIT，直接返回 `status="skipped"` 并记录 `unavailable_reason`，**不返回当前数据冒充历史**。这是硬约束。

### 4. 时间对齐与成交模型

```
as_of = 决策日 T 的 15:00（收盘）
  ↓
数据截止：所有 source_time <= T 15:00
  ↓
决策产出（Verdict）
  ↓
成交：T+1 开盘价；若 T+1 停牌 → 顺延至下一可交易日；
      若 T+1 一字涨停（买入）/ 一字跌停（卖出）→ 顺延，最多顺延 3 日，否则记为无法成交
  ↓
持有期结束：T+1+N 个交易日收盘价（前复权）
```

- 复权：统一用前复权序列（`pro_bar(adj='qfq')`），避免分红送转造成假收益。
- 基准：A 股沪深 300（`index_daily` 000300.SH），美股标普 500，ETF 用跟踪指数，基金用同类平均。
- 无风险利率：`bond_zh_us_rate` 或固定 2%，仅用于 Sharpe 计算。

### 5. 指标定义

| 指标 | 定义 | 用途 |
|---|---|---|
| `hit` | `sign(stance_score) == sign(future_return)` | 方向命中率 |
| `alpha` | 个股收益 − 基准收益（同持有期） | 相对能力 |
| `Brier` | `mean((conviction − hit)^2)` | 置信度校准（越低越好） |
| `calibration_table` | conviction 分桶 [0,.4) [.4,.6) [.6,.8) [.8,1] 的实际命中率 | 直观看是否过度自信 |
| `debate_lift` | 有辩论组命中率 − 无辩论组命中率 | 辩论价值 |
| `analyst_ablation` | 去掉某分析师后的命中率变化 | 贡献度 |
| `stability` | 同一决策点 3 次运行的 stance 一致率 | 可靠性 |
| `mdd` | 按决策序列构造的净值最大回撤 | 辅助 |

`stance_score`：bullish=+1，neutral=0，bearish=−1；neutral 的 `hit` 定义为 `|return| < 阈值`（阈值按持有期设，如 20 日 ±3%）。

### 6. 样本设计

- 资产池：默认 20-30 只覆盖 3-5 个行业；用 `index_weight` 取历史成分。
- 决策点：每周一个（周五收盘），覆盖至少 12 个月 → 约 50 点/资产。
- 市场状态分层：上涨 / 震荡 / 下跌各至少 20% 样本，否则分组统计不可信。
- 最小样本：单组 ≥ 30 才能报命中率；不足则只报原始记录，不报比率。

### 7. 成本估算

| 项 | 单决策点 | 100 点 | 3 次重复 |
|---|---|---|---|
| LLM 调用 | 20-25 | 2000-2500 | 6000-7500 |
| 工具调用 | 25-32 | 2500-3200 | 7500-9600 |
| 预计时长 | 3-6 min | 5-10 h | 15-30 h |

结论：回测必须支持断点续跑（每个 decision 完成即落库，按 `run_id + asset + as_of` 幂等）与 LLM 响应缓存。否则跑一半失败等于白跑。

### 8. 反作弊清单（每条都要在代码里有对应实现）

| 陷阱 | 实现层对策 |
|---|---|
| 未来函数（用了 as_of 之后的数据） | 数据层过滤 + `PIT_MODE` 断言 |
| 财务数据用报告期而非公告日 | 统一按 `ann_date` 过滤 |
| 当日收盘决策当日成交 | 强制 T+1 开盘 |
| 不复权 | 统一前复权 |
| 停牌/涨跌停照常成交 | `clock.py` 判定可成交性 |
| 幸存者偏差 | 历史成分股 |
| 财报重述 | 用 `f_ann_date` + 首次披露值（tushare 提供 `update_flag` 时按首次） |
| 只报最好的一组参数 | 回测报告必须列出全部参数组合，不允许挑选 |
| 新闻回测用现在搜到的内容 | 回测模式禁用无时间戳来源 |

### 9. 代码结构

```
src/backtest/
├── __init__.py
├── clock.py          # 交易日历、T+1、停牌/涨跌停、持有期计算
├── universe.py       # 历史成分股，防幸存者偏差
├── datasource.py     # PIT 数据源包装（as_of 过滤）
├── runner.py         # 决策点遍历、幂等、断点续跑
├── cache.py          # LLM 响应缓存（输入 hash）
├── metrics.py        # hit / alpha / Brier / calibration / ablation
└── report.py         # JSON + 表格输出
```

与主链路的关系：`runner` 调用 `pipeline.run()`，只注入不同的 `Clock` 与 `DataSource`，不改编排代码。

### 10. 回测验收

1. 同一 `run_id + asset + as_of` 重跑，结果从缓存读取，数值完全一致。
2. 构造一个"必然错"的案例（如用 T+1 数据做决策），PIT 断言必须抛错。
3. 一个已知除权日的股票，前复权收益计算与手工核对一致（误差 < 0.01%）。
4. 100 个决策点的回测可在断点后继续，不重复计算已完成项。
5. 回测报告中，新闻类证据全部标记为 `unavailable`，且没有任何一条来自 ddgs。
